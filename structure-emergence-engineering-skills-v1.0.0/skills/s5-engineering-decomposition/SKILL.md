# S5：工程解构、分解与重构

## 目的
把分析结果转成可以实现、集成、测试与维护的工程结构。

## 触发条件
用户需要流程、工具、产品、系统、Agent、数据管道、业务操作或可执行方案时。

## 输入
S1–S4中与任务相关的模型、目标交付物、资源限制、现有工具和技术环境。

## 步骤
1. 从验收目标反推必需能力，拆分为组件/子任务；优先按高内聚、低耦合切分。
2. 每个组件定义单一职责、输入、输出、状态、错误类型和副作用。
3. 定义接口契约：字段、类型、单位、协议、鉴权、时限、重试与幂等行为（适用时）。
4. 画出依赖图和数据/控制流；标记单点故障、循环依赖、权限边界和外部依赖。
5. 估算资源和约束：开发时间、算力、成本、人工、存储、延迟、法规/安全和维护负担。未知数给区间或待测标记。
6. 决定哪些模块复用现成工具、哪些自行实现、哪些应暂缓；避免“为了架构而架构”。
7. 设计最小闭环：输入→处理→输出→观测→反馈。必要时给降级方案和人工接管点。
8. 为每个组件定义单元测试/契约测试和失败后的恢复策略。

## 输出
工程架构图、组件清单、接口契约、依赖/风险清单、资源估算、最小实施顺序。

## 验收标准
- 所有关键组件有输入、输出、责任边界和测试方式。
- 架构可映射到实际工具或明确的待选工具，不是纯流程图。
- 能以有限资源完成一个闭环，并有错误处理和人工接管路径。

## 失败判据
接口含糊；依赖未声明；关键组件无法独立测试；过早拆成大量微服务/Agent；没有安全、回滚或人工接管方案。

## 工具/模板
可使用组件契约表：组件ID、职责、输入、输出、依赖、错误、测试、资源与Owner。按需引用`templates/mvp-validation-card.md`。

## 信息源需求
对技术规格、API、许可、成本、部署要求和安全要求调用S8，并优先查官方文档/代码/标准。
