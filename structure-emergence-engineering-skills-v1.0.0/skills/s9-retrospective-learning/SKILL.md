# S9：复盘迭代与知识沉淀

## 目的
让每轮迭代改变模型或执行方式，并能说明为什么改、改了什么、是否真的改善。

## 触发条件
MVP结束、预期与实际出现差异、来源更新、系统运行异常、关键假设被支持/反驳，或准备复用既有分析时。

## 输入
原始假设与预期、测试协议、真实结果、数据/日志、来源更新和历史版本。

## 步骤
1. 对照预期与实际，量化差异；数据不足时定性说明并保留不确定性。
2. 将误差初步归类到L0–L7：前提/边界、结构、变量/测量、状态规则、涌现机制、工程执行、观测验证、迭代治理。
3. 不急于选定唯一根因；列出竞争诊断并寻找能区分它们的证据。
4. 决定是修订假设、补充对象、重定义变量、改状态规则、修改组件、修正观测，还是暂时不改模型。
5. 写明变更前后差异、证据依据、影响范围、回滚条件和预期改善指标。
6. 保留旧版本、数据、配置和测试协议；对新版本运行回归测试，防止只在新案例上“变好”。
7. 沉淀为可复用规则/模板，但把适用范围与失效条件一起保存。
8. 更新下一轮验证优先级，停止没有新信息价值的重复优化。

## 输出
复盘记录、版本变更、根因假设、回归测试结果、下一轮决策与可复用知识单元。

## 验收标准
- 每次修改都可追溯到具体观察或证据。
- 保留旧版本并说明影响范围；重大变更有回归测试或清楚标注尚未测试。
- 区分真实改进、环境变化、随机波动和测量口径变化。

## 失败判据
只写感受或结论；事后改写成功标准；为迎合结果而调整模型却不说明；不断增加复杂度而不验证收益；反复重做但没有留下可复用记录。

## 工具/模板
`templates/retrospective-version-log.md`、`templates/mvp-validation-card.md`。

## 信息源需求
如果复盘发现外部事实或技术状态发生变化，调用S8；若根因仅是内部执行流程，可先用日志验证。
