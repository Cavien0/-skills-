# S6：MVP交付与验证

## 目的
用最小成本验证最重要的假设、关键转移或工程闭环，并明确结果能证明和不能证明什么。

## 触发条件
存在需要验证的设计、策略、流程、模型、产品或因果机制；或方案在扩大投入前需要快速验证时。

## 输入
关键断言/假设、S5组件清单（若工程任务适用）、资源上限、可用数据、成功目标。

## 步骤
1. 选一个对决策影响大、但当前不确定且可在有限成本下检验的断言。
2. 确定最小交付物，确保真实使用目标输入并能产生可检查结果。
3. 优先选择能区分竞争解释的测试，而不是只展示方案“可以运行”的演示。
4. 在测试前写明基线/对照、数据范围、时间窗、成功指标、失败判据、无结论条件和停止规则。
5. 限定资源、成本和期限；记录偏离测试协议的情况。
6. 实际运行并保存输入、版本、配置、日志与结果，保证可复核。
7. 把结果归为支持、反驳、混合或无结论；不要把未失败当作已证明。
8. 依照预设规则决定继续、修改、扩大、暂停或停止。

## 输出
最小交付物、MVP验证卡、结果证据、决策建议和剩余未知。

## 验收标准
- 存在可运行/可使用的最小交付物或真实测试结果。
- 测试前已有判据，实际结果可与基线或目标比较。
- 明确区分验证了功能、支持了假设，还是证明了因果；三者不是一回事。

## 失败判据
只有概念图或演示视频；成功标准在看过结果后才改变；没有基线；忽略失败数据；把单次成功泛化到所有场景。

## 工具/模板
`templates/mvp-validation-card.md`。

## 信息源需求
若MVP依赖外部数据、标准或技术接口，调用S8；若测试结果将影响高风险决策，应提高证据要求并增加独立复核。
